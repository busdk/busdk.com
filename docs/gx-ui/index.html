Bus GX/UI Library

Typed Go components for frontend products.

Bus GX/UI Library lets Go teams write frontend UI as typed components with HTML-like .gx markup, compile it into Go, and reuse checked component families across portal modules without moving product policy away from Go.

Start the tutorial Browse components Reference docs

What it is for

This product is for Go developers, platform engineers, BusDK module authors, and AI-native engineering teams that want frontend code to sit next to product models, pass through ordinary Go review, and render deterministically in tests.

Author typed GX components

Use .gx files for markup-shaped Go functions, typed props, callback functions, children, intrinsic elements, and generated Go output.

Use Bus UI primitives

Compose shells, navigation, fields, tables, status, files, evidence, terminals, and assistant controls through checked Go APIs.

Wire runtime and tests

Mount component trees, dispatch actions, call host resources, test render output, and bridge to Go/WASM when a browser host is used.

Build product surfaces

See portal pages, provider errors, uploads, evidence, AI workbenches, terminal sessions, and module-owned policy.

Developer workflow

  • Write HTML-like .gx components in the same package as the Go presenter.
  • Pass ordinary Go values, typed props, and callback functions into component tags.
  • Compile GX source into generated Go rendering.
  • Use shared checked components for shells, forms, status, tables, evidence, terminal, assistant, and portal surfaces.
  • Keep validation, authorization, provider behavior, secrets, and business policy in the owning product module.

Code shape

GX source looks like Go with markup in place. Generated output remains Go, so the same package can test rendering, adapter behavior, and product policy together. 

package portalui

func EvidenceCard(props EvidenceCardProps) gx.Node {
  return <article class="evidence-card">
    <h2>{props.Title}</h2>
    <EvidencePreview evidence={props.Evidence} />
    <EventBar items={props.Actions} />
  </article>
}

The same package can render the card on the server, mount it through the browser runtime, and verify the output with deterministic Go tests before product code wires real data into it.

What is implemented

The current library covers the surfaces used by Bus portal modules: app and page shells, navigation, tabs, panels, status states, event bars, fields, filter toolbars, submit controls, file inputs, drop zones, evidence links and previews, projection details, provider errors, dense tables, text tables, summary rows, record lists, terminal panels, assistant workbench controls, model selection, approvals, review state, and thread-isolation UI.

Policy-heavy behavior stays explicit in Go. URL checks, upload rules, evidence access, redaction, provider errors, trusted slots, callbacks, reducers, and authorization boundaries remain owned by the product module or shared Go adapter.

Modules behind the product

bus-gx owns the source format, compiler, render tree, runtime bridges, callback/event plumbing, and test utilities. bus-ui owns reusable checked components, adapters, CSS hooks, mount helpers, portal integration surfaces, and test harnesses.
