Bus Engine OS

The modules behind the OS product line.

Bus Engine OS is one product outcome, but the implementation should keep OS composition, artifact storage, API control, runtime execution, and provider-specific virtualization in separate ownership boundaries.

Core product modules

ModuleRoleWhat users see
bus-engine-osOperating-system build pipeline.Source manifests, package recipes, kernel profiles, root filesystem assembly, image builds, and boot-test evidence.
bus-artifactsUser-facing artifact CLI and client library.Artifact catalogs, downloads, checksum verification, mirrors, and updates without storing large binaries in Git.
bus-api-provider-artifactsAPI controller for artifact operations.Hosted artifact catalog access for tools, environments, and product UIs.
bus-integration-artifactsArtifact business logic and storage integration.Verified downloads, local mirrors, catalog state, and provider-backed storage operations through Bus Events.

Runtime and provider modules

ModuleRoleBoundary
bus-engineCLI and client surface for Linux-backed runtime environments.Consumes OS images; does not own OS composition.
bus-api-provider-engineAPI controller for Engine runtime actions.Accepts API requests and delegates through Events.
bus-integration-engineEngine runtime business logic.Coordinates VM-backed runtime lifecycle and shared Engine behavior.
bus-integration-vmGeneric VM lifecycle integration.Keeps provider-neutral VM behavior above QEMU, cloud, or future providers.
bus-integration-qemuLocal QEMU provider.Boots and tests images locally, including non-accelerated fallback when hardware virtualization is unavailable.

Update path

OS updates should be treated as artifact and policy changes, not ad hoc machine mutation. The long-term path connects Bus Engine OS package/image outputs to Bus update infrastructure so environments can receive verified kernel, rootfs, and image updates with provenance and rollback planning.

Why the split matters

The OS builder should not become the runtime controller, and the runtime controller should not become a package manager. Keeping these boundaries clear makes the product easier to test: package archives can be validated without starting a VM, QEMU can boot-test an image without knowing how every package was built, and artifact mirrors can verify checksums without knowing the workload.
