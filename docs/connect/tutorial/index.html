Bus Connect

Set up the proof of concept.

This builds a working paid message endpoint: an x402 challenge, a settled payment that opens exactly one thread, a capability that reads only that thread, free bounded follow-ups, and recovery from a payment interrupted at the worst possible moment. Everything runs on your own machine.

What you will and will not have at the end

You will have the complete protocol working against real durable storage, with the same binary and the same code paths a hosted instance would use.

You will not have a public endpoint that takes real money. The current build refuses any non-loopback listen address or facilitator URL, and settles against a local fake facilitator rather than a payment network. That restriction is deliberate: it means you cannot accidentally move funds while evaluating. The last section lists what is still required before hosted paid operation.

Before you start

You need a Bus source checkout, Go, GNU make, and curl. Bus Connect depends on the Bus Events and Bus Help module sources, so build it from a checkout that has its sibling modules present rather than as a standalone clone. 

cd bus-connect
make clean build install
bus-connect --version

make install places the binary in ~/.local/bin by default. Add that to your PATH if it is not there already.

Step 1: create the instance key

One key per running instance derives every thread capability. It never leaves the process, and it is what makes an interrupted payment recoverable: the same payment and body always re-derive the same capability. Keep it secret and keep it stable, because rotating it invalidates every existing thread capability. 

head -c 32 /dev/urandom | xxd -p | tr -d '\n' > capability.key
chmod 600 capability.key

Step 2: start a settlement facilitator

A facilitator is the component that actually settles a payment and can later be asked, authoritatively, what happened to one. The repository ships a local fake for development. It records settlements durably and can be told to withhold its answer, which is how you reproduce the failure that matters. 

go build -o fakefacilitator ./tests/fakefacilitator
mkdir -p facilitator-state
./fakefacilitator 127.0.0.1:9402 ./facilitator-state &

Step 3: run the daemon

Start with the file store. It is durable across restarts and needs no other service, which makes it the right choice for a first run. Step 7 moves the same daemon onto Bus Events. 

bus-connect serve \
  --listen 127.0.0.1:8402 \
  --pay-to 0x000000000000000000000000000000000000dEaD \
  --capability-key-file ./capability.key \
  --facilitator-url http://127.0.0.1:9402 \
  --store file --store-file ./conversations.log

Replace --pay-to with the address that should receive initiation fees. Nothing settles to it in this tutorial, but it is what the challenge advertises, and a payment naming a different destination is rejected.

Step 4: see what an unpaid caller gets

curl -s http://127.0.0.1:8402/v1/threads \
  -X POST -H 'Content-Type: application/json' \
  -d '{"message":"hi"}'

The response is 402 with the exact tuple a payer must match: protocol version, scheme, network, asset contract, decimals, atomic amount, and destination. It also carries the terms, which state that the fee is non-refundable and guarantees no response. The same document is served at /.well-known/x402 for discovery.

Step 5: open a thread with a payment

Bus Connect never creates a payment authorization. It holds no signer, seed, or wallet key, and cannot send funds. The contacting side signs elsewhere and presents the envelope. For this tutorial, write one by hand. 

cat > payment.json <<'JSON'
{"x402Version":2,"scheme":"exact","network":"eip155:8453",
 "asset":"0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913","amount":"20000",
 "payTo":"0x000000000000000000000000000000000000dEaD",
 "from":"0xSomeAgentWallet","nonce":"demo-1","signature":"demo-signature-1"}
JSON

printf 'Hello, I would like to talk to you.' > message.txt

bus-connect create --api-url http://127.0.0.1:8402 \
  --body-file message.txt --payment-file payment.json

You get back a thread id, the state active, one message, and one capability. Save the capability: it is issued once, on the response that creates the thread, and on an exact replay of that same request. It is never echoed by a read.

create and get are ordinary HTTP clients of the same REST surface any client uses. They reject every server-side store option, so neither can be pointed at your storage.

Step 6: exercise the behavior that matters

Each of these is worth running, because each is a place a payment endpoint usually gets something wrong.

The same payment presented twice. Run the create from step 5 again, unchanged.

bus-connect create --api-url http://127.0.0.1:8402 \
  --body-file message.txt --payment-file payment.json

Same thread id, same capability, still one message. This is the lost-response path: a client that never saw the first answer can safely retry and will not be charged for a second thread or lose the first one.

The same payment with a different message. Edit message.txt and retry. You get 409 authorization_body_conflict. One authorization is bound to one message body, so a settled payment cannot be reused to send something else.

A payment that does not match the challenge. Change network to eip155:1 and retry. It is rejected before the facilitator is contacted at all, so a wrong tuple never reaches settlement.

A free follow-up, sent twice.

curl -s http://127.0.0.1:8402/v1/threads/THREAD_ID/messages \
  -X POST -H "Authorization: Bearer CAPABILITY" \
  -H 'Content-Type: application/json' \
  -d '{"message":"any update?","idempotencyKey":"k1"}'

Run it twice. The thread still has two messages. Reusing that key with a different body is refused rather than silently dropped.

Someone else's capability. Open a second thread with a new nonce, then try to read the first thread with the second thread's capability. It is refused exactly like an unknown capability, so probing cannot map which threads exist.

Secrets in storage and logs.

grep -c 'CAPABILITY' conversations.log daemon.log

Zero in both. Only a keyed digest is persisted, so someone who reads your store still cannot open a thread.

A payment interrupted at the worst moment. This is the one to actually try. Tell the facilitator to settle but withhold its answer, then pay with a fresh nonce.

touch ./facilitator-state/withhold

The request fails with settlement_unresolved. The money moved; the daemon does not know it. Nothing is marked failed, because a lost answer is not a failure. Now restore the answer and repeat the identical request. 

rm ./facilitator-state/withhold

It reconciles into the original thread, active, with exactly one message. You can make this harsher: kill the daemon with SIGKILL while the answer is withheld, restart it, and replay. The outcome is the same, because the durable record survives the process.

Step 7: move to Bus Events storage

The file store is single-process. A real deployment uses Bus Events as the durable authority. The daemon needs an Events endpoint, a service identity token file, and an instance name that selects its aggregate. 

bus-connect serve \
  --listen 127.0.0.1:8402 \
  --pay-to 0x000000000000000000000000000000000000dEaD \
  --capability-key-file ./capability.key \
  --facilitator-url http://127.0.0.1:9402 \
  --store events \
  --events-api-url http://127.0.0.1:8081 \
  --events-token-file ./bus-connect.jwt \
  --instance production

Give Bus Connect its own service identity holding only events:send and events:listen. Do not reuse a broad stack identity. Events scopes both event history and conditional keys to the authenticated identity, so a dedicated identity is what keeps one instance's conversations invisible and immutable to every other identity.

Keep the token in a file readable only by the service account and pass the path, never the token itself. The store requires four behaviors of whatever backend Events runs on: atomic conditional append, deterministic ordered replay, persistence across a restart, and isolation by authenticated identity. Bus Connect does not select or operate that backend.

Repeat step 6 against this configuration. The behavior is identical, and the state now survives an Events restart as well as a daemon restart.

Step 8: shut down

Send SIGTERM. The daemon stops accepting connections, drains within a bounded deadline, closes its store, and exits. If shutdown exceeds the deadline it reports that rather than hanging, and it leaves no background process behind.

Frozen limits

These are enforced, and the advertised terms match what is enforced rather than promising more.

  • Initial message and each follow-up: 16 KiB.
  • 64 message rows per thread. The paid message is row one, so 63 free follow-ups.
  • 100 threads occupying admission at once.
  • 2 settlements in flight at once.
  • 2-second facilitator deadline, 5-second shutdown deadline.

When a limit is reached the request is refused before settlement, so a caller is never charged for a thread that will not be created.

Before this can take real money

The POC above is complete as a protocol. Hosted paid operation needs more, and none of it is implemented today:

The largest item is not in the protocol at all. The exchange tells you a payment settled and gives you a wallet address; it does not tell you who your customer is. Selling a digital service from a Finnish company into the EU means establishing, before the sale completes, whether the buyer is a business or a consumer, where they are, and how to reach them with a receipt — then charging the right VAT, validating a VAT number where one is claimed, honouring the withdrawal right that applies to consumers buying digital services, and retaining all of it. A wallet address supports none of that.

Bus already has the modules for this — customers, entities, VAT, VIES validation, invoices, bookkeeping, and Finnish tax filing — so the work is to route initiation through them rather than to build a second way of recording a sale. Confirm the specifics for your jurisdiction and turnover with your accountant and counsel; nothing here is legal advice.

  • Customer identification and tax treatment at the point of sale, as above.
  • Public exposure. The build refuses non-loopback listen and facilitator URLs.
  • A real facilitator path, proven against the payment network with an approved live check. Base USDC is enabled; Base EURC is allowlisted but disabled until its live path is proven.
  • An operator surface. Reading, replying, and closing threads has no interface yet, and the transport for it is an open decision. The public paid endpoint must not move behind platform authentication, because its callers have no account with you by design.
  • Thread expiry and retention. Both exist as design decisions; neither is applied on a schedule.
  • A durability policy for the Events backend that is appropriate for settled-payment records.
  • Discovery and an OpenAPI description.
