Bus Connect Modules

What is behind the product.

Bus Connect is deliberately small. It is one Go module producing one static binary that contains both the daemon and its thin clients, plus the Bus modules it stores conversations through.

The product module

bus-connect owns the whole product surface: the x402 challenge and payment verification, the settlement state machine, capability derivation, the REST API, and the serve, create, and get commands. The REST API is canonical; the CLI is an unprivileged client of it and holds no separate path to storage.

Storage

bus-events supplies the durable authority. Bus Connect owns a provider-neutral store contract expressed only in its own domain values, so no SQL, driver handle, or connection string crosses that boundary. It requires four behaviors — atomic conditional append, deterministic ordered replay, persistence across a restart, and isolation by authenticated identity — and names no database vendor.

bus-api-provider-events exposes those behaviors over HTTP, and bus-api-provider-identities authorizes the service identity Bus Connect uses. Bus Connect never selects, operates, migrates, or backs up a database itself.

Store providers

Three providers sit behind one contract. events targets a live Bus Events API and is the deployment choice. file is a durable single-process append-only log, useful for evaluation and used by the protocol test gate. memory is test-only and holds nothing across a restart. All three are exercised by the same conformance suite, so the boundary stays honest rather than merely declared.

Supporting modules

bus-help provides shared help and documentation conventions for the CLI. Bus Connect has no dependency on other Bus product modules, and adds no registry, tenancy, webhook, SDK, or platform integration.

Public module documentation is on the documentation site. Private implementation design specifications exist for this module and are not published.
